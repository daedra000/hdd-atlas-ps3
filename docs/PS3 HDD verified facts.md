# Source code settles most HDD Atlas delete rules

The folder names HDD Atlas already deletes are real. **`_INST_` and `_DEL_` are whitelisted by name as direct children of `/dev_hdd0/game/` in the PS3HEN and Cobra/MAMBA payload source.** A Cobra developer thread shows a real install folder, `_INST_2017120306592300114719`, used while NPDRM packages and game updates unpack. No source says what the XMB does with a leftover after a reboot, though, so the rule stays only with confirmation, a stability check and a warning that an interrupted *update* has to be reinstalled. **Where "Update via Internet" stores its download is still unknown.** The only sourced layout is the Update Manager's `/dev_hdd0/updater/NN/*.pup`, and PS3HEN recreates an empty `updater/01` at every start, so only `.pup` files belong on the list, never the folders. **`/dev_hdd0/vsh/task.dat` is a 128 KB fake blank ISO written by webMAN and IRISMAN, not a download index.** The `vsh/task/<id>` and `vsh/game_pkg/<id>` queues use big-endian PDB records in which 0x69 is the task title, and they carry no index file, so the XMB most likely rebuilds the list by scanning the folders. For syscall 840, every source treats the **second output as free space applications can use**; the meaning of the first is disputed. The minimum-free reserve can be read without writing anything, with lv2 peeks at offsets 0x3C and 0x80 of the in-memory UFS2 superblock, which is what webMAN does. **No PS3 file API exposes an inode number or link count**, and webMAN makes hard links in at least four ways, so HDD Atlas can only handle double counting with heuristics. Most remaining unknowns concern Sony's own behaviour: reboot cleanup, the update staging path, and the small per-user folders. The checklist at the end lists the console tests that would settle them.

## 1. `_INST_` and `_DEL_` are real system names, but reboot behaviour is unsourced

**Short answer.** The names are `_INST_<suffix>` (a PKG install's temporary extraction folder) and `_DEL_<suffix>` (a folder being removed by a system uninstall of a game, game update or homebrew). Both sit directly under `/dev_hdd0/game/`. The only real suffix seen is 22 digits, `2017120306592300114719`, whose first 14 digits read as a timestamp. That rests on one example, so match the prefix only. Sony's VSH installer (`game_ext_plugin` `installPKG`) creates `_INST_` whether the install starts from the XMB, the PS Store, PS3HEN or webMAN. None of the homebrew installers (pkgi, IRISMAN, webMAN, ManaGunZ) create or clean these folders. **No source says whether the XMB resumes, removes or ignores a leftover after a reboot.** Deleting one while the system works on it breaks the operation: blocking access caused 80010006 install errors and "data corruption" on uninstall. While HDD Atlas is the running app, the XMB cannot be installing or deleting in the foreground, so a folder seen then is very likely a leftover [inferred]. Deleting a leftover `_DEL_` loses only content the user already chose to delete. Deleting a leftover `_INST_` from a new install loses a partial copy. A leftover from an interrupted **update** may mean the game itself is half-updated; deleting `_INST_` does not fix that, and reinstalling the update should [inferred].

## 3. Download and install queues are big-endian PDB folders with no index file

**Short answer.** A **pending install** `vsh/game_pkg/<id>/` holds `<CONTENT_ID>.pkg` (nearly all of the size), `ICON_FILE` (a PNG with no extension), `d0.pdb`, `d1.pdb` and a **0-byte** `f0.pdb`. A **background download** `vsh/task/<id>/` holds `ICON_FILE`, `d0.pdb` and the `.pkg` target. These facts come from two homebrew generators that copy Sony's layout, plus psdevwiki ("Heavy Rain Episode 1: d0 d1 ICON_FILE"). What a Sony PS Store download leaves is **[unverified]**. PDB files are **big-endian**: a 4-byte zero header, then records of `u32 id | u32 length | u32 length (again) | data`, with no record count, so a parser walks to EOF. Record **0x69 is the task title** ("Package Name (Task Title)"). It is not a clean game title, though: pkgi writes `★ Download "<name>"` or `★ Install "<name>"` and IRISMAN writes `★ Install "<filename>"`. ## 4. Syscall 840's second output is free space; the first needs a console test

**Short answer.** The signature is `int sys_fs_disk_free(const char* path, uint64_t* total_free, uint64_t* avail_free)` (psdevwiki; RPCS3 binds it as 840). **The second output is the free space applications can use** in every source: webMAN's `get_free_space()` returns it, RPCS3's `cellFsGetFreeSize` uses only it, and RPCS3's 2017 implementation copied host `f_bavail` into it. **The first output is disputed.** RPCS3 in 2017 filled it with host `f_bfree` (free space including the root reserve), matching the name `total_free`. webMAN's file manager and PS3MAPI `GETHDDINFO` show it as **device size**, and RPCS3 since 2020 returns roughly free + used. webMAN's usage bar would look nearly empty on every console under the `f_bfree` reading, which favours "capacity", but this is not proven. Pass the mount point (`"/dev_hdd0"`). The minimum-free reserve has no syscall: webMAN's unlockhdd scans lv2 memory for the in-core UFS2 superblock and reads (or pokes) `fs_minfree` at +0x3C and `fs_optim` at +0x80. HDD Atlas can do the read half only. The stock values are 8 and 0.

## 9. `_BU_` trophy backups persist, and `TROPSYS.DAT` indexes every install

Whether TROPSYS.DAT also references `_BU_` folders is unknown, so **`_BU_*` stays off the delete list** and is labelled only.

## 11. No API exposes inodes, so hard links need heuristics

**Short answer.** No PS3 file interface checked exposes an inode number or link count. That covers `CellFsStat` (52 bytes: mode, uid, gid, atime, mtime, ctime, size, blksize), `CellFsDirent` and `CellFsDirectoryEntry`, `CellFsMountInfo` (per mount), the documented fcntl ops, LSN/CDA calls and PSL1GHT's newlib, which zeroes `st_ino` and `st_nlink`. Mamba's kernel-side `CellFsStat` has a trailing `uint64_t dummy[1]` of unknown meaning; it is the one lead worth a console test. **webMAN creates hard links in four ways**: `/stat.ps3<path>&id=<title>` relinks `game/<ID>/USRDIR` files that match a backup by size and MD5 (or size only with `?fast`); its general file copy links instead of copying when both paths are on the internal HDD; PKGLAUNCH links `~tmp.iso` into `tmp/extract`; and prepISO links per-title SFO/PNG files into multiMAN's `cache/`. None of these checks for an existing link. HDD Atlas therefore needs to group likely links, count them once, and reconcile its total against used space.

Run on the HEN console (OFW 4.8x–4.9x) and, where noted, the CECHK03 CFW console, with webMAN FTP for listings. Use throwaway content and back up first wherever saves, trophies or themes are touched.

- [ ] **1. `_INST_` naming and reboot behaviour.** Install a PKG of at least 1–2 GB from XMB "Install Package Files". ## Conclusion

This round mostly moves HDD Atlas's risk from "deleting the wrong folder" to "deleting the right folder at the wrong moment". The rule set itself is now largely grounded in current source. The open questions are about Sony's runtime behaviour: what the VSH does after a reboot with an `_INST_`, `_DEL_` or task folder that has gone missing or been left behind. That only a console can answer, and tests 1–11 should come before any release that widens the delete list. Until then, the safe design is an allow-list matched by prefix, a stability re-check, mandatory confirmation, and plain warnings that tell the user what they will need to reinstall.

The second lesson is that "size on disk" is not a property of a file on a webMAN console. Hard links appear through ordinary webMAN copies, archive launches and prepISO, not only through the dedupe command, and no API reports them. Treating the syscall-840 used-space figure as the ground truth and the per-file sum as an estimate, once test 14 fixes which output is which, will keep HDD Atlas's totals honest even where it cannot tell which names share data.
